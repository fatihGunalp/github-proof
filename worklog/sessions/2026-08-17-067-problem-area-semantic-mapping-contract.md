### 3. Is produced-work evidence mandatory for ProblemArea?

**Canonical sources do not determine one answer.**

What they do say:

- product contract §12: problem areas may be shown "when reliable and bounded
  evidence exists", and the exact evidence requirements are deferred to a
  versioned domain contract;
- P6 §9.4 condition 4 requires "a structured boundary separating declared
  dependencies from produced work", which mandates that the two be
  distinguishable, not that produced-work be present;
- P6 §9.1 and `repository-dependency-evidence.md` §12 state that declarations
  and scaffolds are indistinguishable in the current surface;
- product contract §18 prohibits authorship and originality claims, so
  produced-work evidence may never become an authorship claim.

Bounded options:

**A — produced-work mandatory for every ProblemArea.** Safest against false
positives. Cost: ProblemArea stays fully blocked until a new repository-level
usage evidence surface is contracted and collected.

**B — two distinct evidence kinds (recommended).** Declaration-derived
categorization becomes an explicit *lower-strength repository-level* evidence
kind, clearly named as declaration-derived. Produced-work evidence remains a
separate, stronger kind. Profile-level ProblemArea promotion requires the
stronger kind; the weaker kind may never alone produce a repeated profile
pattern.

Rationale for the promotion restriction: fork and template lineage are excluded
by P2 only through lineage, so two scaffolded non-fork repositories would
otherwise satisfy the P6 two-repository threshold on declarations alone. Option
B keeps that door closed while unblocking repository-level work.

**C — declaration-only evidence never participates in ProblemArea** and stays
technical context. Equivalent to continued deferral with extra vocabulary.

Recommendation: **B**, with the explicit constraint that only the stronger kind
may reach level 5. This is a product decision and requires approval.

## C. Dependency semantic category taxonomy proposal

Not locked. This proposal describes the maximum safe meaning of a *declaration*.
It never describes what a repository builds, solves or proves.

### C.1 Cross-cutting risks that shape the proposal

**Server versus client.** An HTTP client dependency and an HTTP server framework
are different declarations with different meanings. Collapsing them would let
"calls an API" read as "produces an API". They must be separate category keys.

**Declaration versus use.** A declared package may be unused, vendored,
commented out of the code path, or inherited from a template. No category may
imply use. This is exactly why produced-work stays a separate mandatory level
for ProblemArea.

**Framework versus library.** Framework versus library is a package-shape
distinction, not an evidence-strength distinction. Category keys must not encode
"framework" as stronger evidence. Where the distinction changes *meaning* rather
than strength, as with server frameworks versus client libraries, it is encoded
as separate keys.

**Dependency scope is not observable today.** `RepositoryDependencyDeclaration`
carries ecosystem, manifest path, package identity and version literal only. The
Session 066 parser reads runtime and development sections alike
(`devDependencies`, `require-dev`, `[dev-dependencies]`,
`add_development_dependency`), and the normalized shape does not record which
section produced the declaration. A test-only package is therefore
indistinguishable from a runtime package. This materially caps category meaning
and is listed as an open item in section E.4.

### C.2 Proposed category keys

| Category key | Admissible declaration evidence | Maximum safe meaning | Prohibited reading |
|---|---|---|---|
| `data-access` | ORM, query builder and database driver packages | the repository declares a package whose purpose is database or data access | the repository implements persistence, models a domain, or operates a database |
| `http-server` | HTTP/web server frameworks and API frameworks | the repository declares a package whose purpose is serving HTTP endpoints | the repository produces or operates an API |
| `http-client` | HTTP client and API SDK packages | the repository declares a package whose purpose is calling HTTP endpoints | the repository integrates a system, or produces an API |
| `authentication` | authentication and authorization libraries | the repository declares a package whose purpose is authentication or authorization | the repository implements authentication, or is secure |
| `machine-learning` | ML training and modelling frameworks | the repository declares a package whose purpose is machine-learning modelling | the repository performs ML work, or produces ML systems |

Deliberately excluded from the proposal:

- generic numeric or dataframe packages such as `numpy` and `pandas`: they are
  not ML-specific, and mapping them would inflate `machine-learning`;
- containerization: determined by file paths, which are outside the Session 066
  declaration surface;
- domain modelling, integrations, backend, frontend, full stack: no
  deterministic declaration-level determinant, and the last three are role
  labels.

### C.3 Mapping rules

1. Mapping entries are `(ecosystem, packageId) → category`. Bare name matching
   across ecosystems is forbidden.
2. Aliases, renames and successor packages are explicit table entries, never
   heuristics or prefix rules.
3. An unmapped package is unknown. Unknown is never absence and never negative
   evidence.
4. A package may map to at most one category in V1. Multi-category packages are
   left unmapped rather than guessed.
5. No README, topic, description, path or keyword fallback.
6. No weighting, no confidence, no ranking, no locale dependence, no LLM.
7. Category evidence must carry the source declarations it was derived from.

### C.4 What this taxonomy is not

It is not a ProblemArea taxonomy, not an input to ProblemArea qualification on
its own, and not a technical-focus taxonomy. TechnicalFocus remains
language-literal evidence under the P6 contract §8.

## D. Canonical data shape and traceability alternatives

All alternatives must satisfy the four approved invariants: carry
`DependencyCategoryMappingVersion`, preserve source declaration references,
allow deterministic replay, preserve traceability.

### D.1 Alternative 1 — pure on-demand Domain policy, no stored result

A Domain policy maps declarations to categories when a consumer asks. The
returned result carries the mapping version and the source declarations.

- Invariants: all four satisfied, because declarations are already stored in the
  snapshot and the mapping is deterministic and versioned.
- Cost: no persisted category evidence, so any future consumer must re-run the
  mapping and must record which mapping version it used.
- Risk: two consumers could run different mapping versions in one execution
  unless a coherence check is added, exactly like `CrossRepositoryEvidence`
  version checks.

### D.2 Alternative 2 — stored on `RepositorySnapshot`

Rejected. The snapshot is normalized *collected* data. Storing derived semantics
there would blur the collection versus interpretation boundary that Session 066
locked, and would wrongly tie semantic rules to `AnalyzerVersion`.

### D.3 Alternative 3 — stored as a new non-scoring member of `RepositoryAnalysis`

- Invariants: all four satisfied, with the strongest replay guarantee, because
  the category evidence is stored beside the analysis that produced it.
- Cost: changes the locked `analysis-domain-model.md` §2 result shape, adds a
  version-coherence requirement between `AnalyzerVersion` and
  `DependencyCategoryMappingVersion`, and needs an explicit statement that the
  member is non-scoring and absent from the report.

### D.4 Alternative 4 — separate Application-level result composed from the analysis

A `RepositorySemanticEvidence` result composed from a `RepositoryAnalysis`,
carrying category evidence, source declaration references, the mapping version
and a `RepositoryAnalysisReference`. This mirrors how `CrossRepositoryEvidence`
composes over analyses in P5.

- Invariants: all four satisfied.
- Cost: one more result type.
- Benefit: no locked shape change, explicit version carriage, and a natural
  place for the later produced-work rule to compose against.

**Recommendation for approval:** alternative 4, with alternative 3 as the
fallback if one atomic repository result is preferred. Alternative 1 is the
degenerate case of alternative 4 without a result type and is not recommended,
because version coherence would live nowhere.

### D.5 Later rule, reported not locked

`ProducedWorkEvidence + DependencySemanticCategoryEvidence →
RepositoryProblemAreaEvidence` governs qualification, not package mapping, so it
cannot ride `DependencyCategoryMappingVersion`. It will need its own version
owner. No name and no rule is proposed here, per the approved scope.

## H. Dependency Mapping Registry Design Report

No registry file, no package mappings and no production code were created.

### H.1 Package identity normalization

Session 066 `DependencyDeclaration.PackageId` stays the untouched source
literal. Normalization exists only to compute a lookup identity:

    raw source literal        (evidence, never rewritten)
    normalized lookup identity (registry matching only)

Both must be carried, so a matched entry is always traceable back to the exact
declared literal.

Proposed per-ecosystem rules:

| Ecosystem | Canonical identity form | Normalization for lookup |
|---|---|---|
| DotNet | NuGet package id | lowercase invariant; `.`, `-`, `_` preserved |
| Java | `groupId:artifactId` | no case folding; single `:` separator; trim only |
| JavaScript | npm name, scope included as `@scope/name` | lowercase invariant; scope prefix preserved |
| Python | PyPI distribution name | PEP 503: lowercase, then any run of `-`, `_`, `.` collapsed to a single `-` |
| Go | module path | no case folding; strip a trailing major-version element `/vN` where N >= 2 |
| Rust | crate name | lowercase invariant, then `_` mapped to `-` |
| Php | `vendor/package` | lowercase invariant; single `/` separator |
| Ruby | gem name | no case folding; exact ordinal |

Rationale for the asymmetry: NuGet, npm, PyPI, crates.io and Composer treat
identity case-insensitively or publish canonical lowercase names, while Maven
coordinates, Go module paths and RubyGems names are genuinely case-sensitive.
Folding case there would create false matches.

Two consequences that need approval:

- Go's `/vN` stripping means one registry entry covers every major version of a
  module. The alternative is one entry per major version, which multiplies
  maintenance without adding meaning.
- Java and Ruby cannot fold case, so a differently-cased declaration simply does
  not match. That is safe under the unmapped-is-not-absence rule.

Normalization is part of mapping semantics, so it lives in Domain beside the
mapping policy, never in Infrastructure and never in the profile layer.

### H.2 Single canonical truth store

Evaluated against: machine-consumable, human-reviewable, deterministic,
versioned, diff-friendly, no new runtime dependency, no competing store.

| Option | Verdict |
|---|---|
| A. Markdown canonical plus production mirror | Rejected. Two artefacts is a competing truth store unless the mirror is generated, and Markdown table parsing at build time is fragile. |
| B. JSON, single file, embedded into the assembly | **Recommended.** `System.Text.Json` is in-box, so no new dependency. Reviewable as data, diffs one line per entry when formatting is enforced, and production consumes the exact canonical file rather than a copy. |
| C. YAML | Rejected. Requires a new runtime dependency for parsing. |
| D. Strongly typed C# registry | Viable fallback. Zero parse risk and compile-time category safety, but the canonical artefact becomes code, which is harder to review outside the codebase and mixes data with implementation. |
| E. CSV or TSV | Viable but weaker: alias lists and rationale need escaping conventions that reduce reviewability. |

Recommendation: **option B**, with these guards, all enforceable by tests:

1. one canonical file, consumed directly by production, no mirror;
2. deterministic serialization: entries sorted by ecosystem then normalized
   identity, ordinal, one entry per line;
3. schema validation, unique identities, category keys restricted to the locked
   taxonomy;
4. a test asserting the file parses, is sorted and contains no duplicate or
   cross-category conflict.

If the project prefers compile-time safety over data-shaped review, option D is
the fallback and changes nothing else in this design.

### H.3 Registry entry shape

Minimum fields:

| Field | Required | Purpose |
|---|---|---|
| `ecosystem` | yes | scopes the identity; never matched across ecosystems |
| `identity` | yes | normalized lookup identity per H.1 |
| `category` | yes | single category key from the locked taxonomy |
| `aliases` | optional | additional normalized identities that resolve to the same entry |
| `rationale` | yes | the qualifying package property from the contract §8 that justifies the entry |

Decisions:

- **`category` is a single value, never an array.** One package maps to at most
  one category in V1, so the shape makes multi-category assertion impossible
  rather than merely discouraged.
- **No version or range field.** Mapping is identity-based only. Version-scoped
  mapping would require canonical evidence that a package changed purpose across
  versions, which does not exist today and would need a contract change.
- **`rationale` stays inline** in the same artefact. A separate rationale file
  would be a second store. It is metadata: it never participates in lookup, and
  a test asserts it is non-empty.
- **Ambiguous packages are absent from the registry.** There is no "ambiguous"
  or "unmapped" entry type, because unmapped is expressed by absence of an
  entry.

### H.4 Versioning

`DependencyCategoryMappingVersion` is proposed as a semver-shaped identity
carried inside the registry file itself, so the artefact and its version can
never drift apart.

| Change | Bump |
|---|---|
| add a new package mapping | minor |
| add an alias to an existing entry | minor |
| change an existing package's category | **major** |
| remove a mapping or retire a category key | **major** |
| change an identity normalization rule | **major** |
| edit a rationale only | patch |

Major changes are those that can alter a previously produced result for the same
repository, which is exactly when results from two versions must never be
compared or merged.

This version owner is distinct from `AnalyzerVersion` (collection and
normalization), `RuleSetVersion` (scoring), `ObservationRuleVersion` (P5
observations) and `PatternRuleVersion` (P6 taxonomy and promotion), and governs
package mapping only.

### H.5 Taxonomy review from the registry angle

Overlap analysis for the five proposed keys:

- **`http-server` versus `http-client`.** Real overlap exists for frameworks
  that ship both. Rule: primary documented purpose decides; when both are
  primary, the package stays unmapped.
- **`data-access` versus `http-client`.** Data stores accessed over HTTP, such
  as search or document-store clients, would match both by surface reading.
  Rule: a client whose purpose is a specific data store is `data-access`.
- **`authentication` versus `http-server`.** Web frameworks with built-in auth
  must not gain `authentication`; only separately declared auth packages map.
- **`data-access` versus `machine-learning`.** Vector stores and feature stores
  sit between the two and remain unmapped in V1.
- **Meta-frameworks.** Django, Rails, Laravel and similar single packages
  legitimately span serving, data access and authentication. The V1 one-category
  rule therefore leaves them unmapped, which is honest but means some of the
  most common web repositories produce no category evidence at all.

That last point is the main pressure on the taxonomy and is listed as an
unresolved blocker below. The one-package-to-one-category rule is what keeps the
registry honest, so relaxing it would be a semantic change, not a registry
convenience.

### H.6 Coverage limitations at registry level

The invariant "unmapped or unobserved is not category absent" is preserved
structurally:

1. the registry is an **allow-list only**. There is no negative entry form, so
   it is impossible to state that a package is not of a category;
2. there is no default category and no catch-all rule, so an unknown package
   yields no evidence rather than a fallback;
3. the registry is partial by construction and may never be read as an
   enumeration of everything in a category, so "not in the registry" carries no
   meaning about the package;
4. consumers receive positive observations only, and the evidence result carries
   the source availability and completeness state from the contract §6.4, so an
   empty result can always be distinguished from an unavailable one;
5. the .NET `http-server` asymmetry cannot be repaired at registry level,
   because such repositories never produce a declaration to match. It stays a
   documented coverage asymmetry, and category absence remains meaningless.

### I.2 Manifest package identity and alias audit

Question: does `RepositorySnapshot.DependencyDeclarations.PackageId` carry the
real dependency package identity, or only the manifest-local key?

**Answer: it depends on the format. Two formats currently record a
manifest-local key, not the package identity.**

Code evidence:

- `GitHubRepositoryDependencyManifestParser.cs:241` — for npm and Composer the
  identity is `dependency.Name`, the JSON object key.
- `GitHubRepositoryDependencyManifestParser.cs:360` — for Cargo the identity is
  `entry.Key`, the TOML table key. `TomlSubsetReader.ReadInlineTableVersion`
  (line 616) extracts only `version` from an inline table, so a `package =`

Concrete false results:

npm alias, `package.json`:

records `PackageId = "lodash"`. If the registry maps npm `lodash`, this is a

    "dependencies": { "my-orm": "npm:sequelize@^6.0.0" }

records `PackageId = "my-orm"`, a **false negative** for a real ORM declaration.

records `PackageId = "db"`, a false negative; and

records `PackageId = "serde"`, a false positive.

Full per-ecosystem audit result:

| Ecosystem | Identity carried today | Risk |
|---|---|---|
| JavaScript (npm) | manifest key | **alias `npm:` substitution breaks identity, both directions** |
| Rust (Cargo) | table key | **`package =` rename breaks identity, both directions** |
| Php (Composer) | manifest key | key is the real `vendor/package`, but platform requirements such as `php` and `ext-json` are recorded as if they were packages (line 241, no filter) |

| Java (Maven) | real `groupId:artifactId` | `Descendants()` (line 158) also matches `dependencyManagement` entries, which declare versions rather than dependencies; `${property}` placeholders are recorded literally |
| Java (Gradle) | real coordinate | version-catalog references such as `libs.spring.boot` produce no declaration, and `libs.versions.toml` is outside the Session 066 manifest set |

### I.3 Bounded amendment options, reported not applied

Option 1 — registry-side mitigation only. Never map identities that are known
to be ambiguous, and accept alias-caused misses as unmapped. This does not fix
false positives, because a wrong identity can still match a legitimate entry.
Cheapest, weakest.

Option 2 — bounded additive parser amendment. Resolve npm `npm:` aliases and
Cargo `package =` renames to the real identity, exclude Composer platform
requirements, exclude Go `// indirect` requires, and skip Maven
`dependencyManagement`. Both alias cases are locally detectable: the npm alias
appears in the version literal, and the Cargo rename appears in the inline
table.

Option 3 — split the shape so the declaration carries both the manifest-local
key and the resolved identity. Most faithful, largest change, and it reopens the
Session 066 normalized shape.

Version impact of options 2 and 3: they change previously produced snapshot
values, which `repository-dependency-evidence.md` §9 classifies as a **major**

next value would be `0.3.0`; a literal reading of the rule gives `1.0.0`. This

### I.4 JSON loading architecture boundary

Domain must not know JSON. Approved boundary:

    canonical versioned JSON registry
    → non-Domain loader / adapter
    → typed, validated Domain registry

Placement proposal:

- **Domain** owns the category type, the typed immutable registry, the mapping
  invariants, validation and deterministic lookup semantics, including the
  normalization rules of §I.1, and exposes a constructor that accepts already
  parsed entries.
- **Infrastructure** owns the loader: reading the embedded canonical artefact,
  JSON deserialization, and constructing the Domain registry. This matches the
  existing rule that provider and format concerns live in Infrastructure.
- **Web** composes the loader once at startup, exactly as it composes the
  snapshot orchestrator today.

Consequence: `System.Text.Json` never appears in Domain, and no second truth
store exists, because the loader produces the Domain type from the one canonical
file.

Alternative placement, if Application should not depend on Infrastructure for
this: the loader may live in Application instead, since it needs no HTTP. Either
placement satisfies the boundary; the choice is a wiring decision.

### I.5 Revised taxonomy proposal

`http-server` is withdrawn from the V1 lock. Proposed V1 set:

- `data-access`
- `web-application-framework`
- `http-client`
- `authentication`
- `machine-learning`

`web-application-framework` specification:

- **Maximum meaning:** a declaration was observed whose package purpose is
  providing a general web application framework.
- **Qualifying package properties:** the package's own primary purpose is
  offering an integrated framework for building web applications, typically
  covering routing and request handling as a framework rather than as a library.
- **False-positive boundary:** HTTP client libraries, template engines,
  standalone routers, testing utilities and asset build tools do not qualify.
- **Explicit non-meaning:** it does not imply authentication, data access, API
  production, backend experience, deployment or operation. A framework's
  embedded feature set never produces a second category.
- **Ambiguous, unmapped in V1:** micro-frameworks and bare HTTP server libraries
  that are not general application frameworks; these remain uncovered until
  `http-server` is separately contracted.
- **Alias behaviour:** explicit registry entries only, including packages split
  or renamed across major versions.
- **Illustrative SHOULD map:** a broad web application framework package.
- **Illustrative MUST NOT map:** an HTTP client; a template engine; a bundler.

This resolves the meta-framework blocker without multi-category mapping: broad
frameworks now have exactly one honest category, and their embedded features
stay unclaimed. The remaining gap is minimal HTTP servers, which is smaller and
explicitly documented rather than silently mismapped.

The one-package-to-one-category rule stands. No package may produce two
categories in V1.

### I.6 Replay and versioned registry strategy

A single mutable file is **not sufficient**. If a result carries
`DependencyCategoryMappingVersion` 1.0.0, replay requires the 1.0.0 mapping,
which an overwritten file no longer provides at runtime. Version control gives
history to humans, not to a running process.

Recommended: **immutable versioned artefacts**, one file per mapping version,
with these rules:

1. a published mapping version is never edited; a change produces a new file;
2. each file carries its own version internally, and the loader rejects a file
   whose internal version does not match its identity;
3. exactly one version is active for a given execution, selected explicitly by
   composition, never implicitly by "latest file wins";
4. historical versions are inactive immutable rule versions, not competing
   truth, exactly as older `PatternRuleVersion` semantics would be;
5. a retention rule states which historical versions must remain present for
   replay of persisted results.

Exact directory layout and file naming are not locked here.

### I.7 Rationale rule

`rationale` is non-semantic metadata. Recommended structural guarantee: the
loader validates that it is present and non-empty, then **does not carry it into
the Domain registry at all**. Runtime results then cannot depend on it, by
construction rather than by convention.

Rationale-only change is a patch version.

### K.7 Minimum coverage strategy

**A. Does every category need representation in every ecosystem?** No. Requiring
balance would force ambiguous packages into the registry, which trades a real
correctness guarantee for a cosmetic one. Coverage is explicitly the lesser
value.

**B. Should some cells stay empty on purpose?** Yes, exactly the cells in §K.6.
An empty cell is a statement about the registry, never about the ecosystem or
the repository.

**C. How are gaps presented?** As coverage limitations, never as absence:

1. the registry is an allow-list with no negative entry form, so it cannot
   express that a package is not of a category;
2. an unmapped or absent package produces no evidence at all, rather than a
   negative observation;
3. consumers carry the `dependency-manifests` availability and completeness
   state, so an empty result is always distinguishable from an unavailable one;
4. the registry is partial by construction and may never be read as an
   enumeration of a category;
5. the ecosystem asymmetries in §K.6 and the parsing limitations in
   `repository-dependency-evidence.md` §11.1 are quoted wherever category
   evidence is surfaced.

### N.3 Domain model and policy

`DependencyCategoryRegistry` is typed and validated: duplicate
`(ecosystem, lookup identity)` pairs are rejected, entries are ordered
deterministically, and `Resolve` returns null for an unmapped package.

`DependencyIdentityNormalizer` implements the locked lookup rules: invariant

preservation for Java, Go, Rust and Ruby. The source `PackageId` is never
rewritten.

`RepositorySemanticEvidencePolicy` derives `RepositorySemanticEvidence` from one
analysis and one registry. Each category becomes exactly one observation with
one or more supporting declarations, and no count, weight or score exists
anywhere in the result.

### N.4 Infrastructure boundary

Domain contains no JSON, stream, resource or file API. The loader owns
deserialization, validates that each entry declares a rationale and then drops
it, rejects unknown ecosystems and category keys, rejects identities that are
not already in normalized lookup form, and rejects an artefact whose declared
`mappingVersion` does not match the version it was loaded as. Exactly one
version is selected explicitly per execution.

### N.5 Availability and absence

`RepositorySemanticEvidence` carries the `dependency-manifests` availability and
the declaration completeness flag, and exposes `IsCategorySurfaceComplete` only
when both hold. Unavailable, unrecorded, incomplete and unmapped are all
distinct from absence, and the tests lock each case.
